# `okfctl-api` — an HTTP API plugin over an OKF bundle

**Status:** Proposal (design) · **Owner:** Casey West · **License:** Apache-2.0
**Depends on:** `okfctl` core (`internal/okf`, `graph`, `search` core, `okfctl-search`
plugin, ADR 0002/0004/0005/0006), consumed by `cwest/office`.
**Spec posture:** okfctl conforms to OKF; this proposal invents zero spec rules. It
is a *consumption* layer over what `internal/okf` already parses. Tool + corpus stay
pinned at OKF v0.1; this plugin does not close that gap (AGENTS.md: "do not close
it as a side effect").

---

## 0. Problem statement

`cwest/office`'s dashboard currently gets everything it renders from five
generate-time artifacts (`office_data/generate_data.py` → `data/{graph,index,
concepts,log,search}.json`), produced by a **vendored copy of `okf` Python code**
(`office_data/_vendor/okf/{corpus.py,embed.py}`) that duplicates parsing and
embedding logic already implemented, more strictly, in `okfctl`/`okfctl-search`
(Go). This has three costs:

1. **Duplication drag.** Two parsers (Go in okfctl, Python in the vendored `okf`
   package) must agree on link resolution, neighborhood derivation, and frontmatter
   reads, kept in sync only by a manual `tools/sync-okf-vendor.sh` re-copy plus a
   drift test (`test_okf_vendor_sync.py`) that can only compare bytes, not
   semantics.
2. **Staleness by construction.** `data/*.json` is committed and regenerated by a
   `refresh.py` hook (launchd timer / git-hook triggered) — the dashboard is never
   fresher than the last regenerate, and a regenerate is a multi-step pipeline
   (fast-forward KB clone → `generate_data.py` → per-room `generate.py` builds)
   that can fail partway.
3. **No live query surface.** Filtering, pagination, and search all happen
   client-side over a fully-materialized JSON blob (`search.json` is 285KB for
   ~239 nodes' worth of 256-dim vectors) baked in at generate time. There's no way
   to ask "give me page 2 of `Concept` nodes modified this month" without shipping
   the whole index.json to the browser first.

This proposal designs `okfctl-api`, an HTTP server plugin that serves the same
information *live*, off the same bundle `okfctl` already understands, so office can
delete its vendored parser and treat okfctl as the single source of bundle truth.

## 1. Plugin, subcommand, or `graph serve` extension? — **Recommend: new plugin**

Three options were on the table.

### Option A — extend `graph serve`/`serve`
`cmd/serve.go` already runs a stdlib `net/http` server with `newServeHandler(b)`
exposing `GET /` (embedded vanilla-JS visualizer) and `GET /graph.json`. Bolting a
JSON API onto it would mean growing that mux with `/api/nodes`, `/api/search`,
etc., inside core.

**Rejected.** Two reasons, both load-bearing:

- **ADR 0006 scope.** `serve` is explicitly the *visualizer's* server — a
  single embedded HTML page plus its one data endpoint, chosen for zero build
  step and minimal surface (ADR 0006: "right-sized for the current read-only
  viewer"). Growing it into a general REST API is a materially more ambitious
  front-end/server than that ADR sized for; ADR 0006 itself says such growth
  "would justify revisiting it with a follow-on ADR." A second, unrelated
  consumer (office) is exactly that trigger, and the honest move is a new
  surface, not silently expanding `serve`'s contract.
- **Core stays dependency-light, but semantic search needs `okfctl-search`'s
  weight.** office's search endpoint needs the flat vector store and the pure-Go
  embedder — both currently plugin-only (ADR 0002, ADR 0004, ADR 0005) precisely
  so core doesn't carry that weight. An API server embedded in `serve` (core)
  would either (a) reintroduce that weight into core, undoing ADR 0002's whole
  point, or (b) have `serve` shell out to `okfctl-search` at request time, which
  is a worse architecture than just building the API as its own plugin that
  imports `internal/search` directly.

### Option B — a new built-in subcommand, `okfctl api serve`
Ship it as core-tree command like `graph`/`search`, not a `PATH`-dispatched sibling
binary.

**Rejected.** Same weight argument as above: if the API is to expose semantic
search (§4 below), it must link `internal/search`'s embedder + store, which is
today plugin-only weight by design (ADR 0002/0004/0005). Making it a built-in
subcommand means either dragging that weight into the core binary (breaking the
"core is a single self-contained binary with no [heavy] runtime dependencies"
promise, PRD §5.1) or having the built-in shell out to `okfctl-search`, which is
an uglier and slower architecture than a plugin that links the library directly.
A built-in subcommand is also wrong precedent: it says "API serving is core,"
when in fact it is exactly the kind of optional, consumer-specific capability
(one dashboard, not every okfctl user) the plugin boundary exists for.

### Option C — a new plugin, `okfctl-api` — **Chosen**

Ship `okfctl-api` as a sibling static binary discovered by the existing
`internal/plugin` PATH-dispatch mechanism (ADR 0002), dispatched as
`okfctl api serve [bundle-dir]` exactly the way `okfctl-search` is dispatched as
`okfctl search --semantic`. This is the smallest change that is architecturally
honest:

- It composes with, rather than duplicates, `graph`/`search`/`okfctl-search`:
  `okfctl-api` **imports `internal/okf`, `internal/search`, and reuses
  `okf.BuildGraph`/`okf.Search`/`okf.Neighborhood`/`search.Query`/`search.Related`
  directly as a library** (same-process function calls — not shelling out to
  another CLI at request time, which would be slow and fragile). This is legal
  and intended: `internal/*` packages are already consumed by two binaries
  (`okfctl` core and `okfctl-search`); a third consumer is exactly the pattern
  ADR 0002 anticipated when it kept `internal/plugin` stdlib-only and dispatch
  data-driven.
- It inherits ADR 0002's tradeoffs explicitly and by design: cross-process from
  `okfctl` core (it reloads the bundle itself, in-process, at its own startup —
  see freshness in §3), no compile-time contract with core beyond the
  `okfctl-<name>` naming convention, discovered via `PATH`/`plugin install`.
- **It is a long-running server, an outlier among today's plugins/subcommands**
  (`okfctl-search` and every core subcommand are one-shot). That's fine: nothing
  in ADR 0002 requires a plugin to exit immediately, and `serve` already
  establishes long-running-server-as-subcommand precedent inside core — this is
  the same shape, one plugin-boundary hop to the left because of the weight it
  carries.

**What this costs, honestly:** an `okfctl-api` process holds its own in-memory
`*okf.Bundle` and its own loaded `*search.Store`, entirely separate from any
concurrently-running `okfctl serve` process's bundle. Two servers, two bundle
loads, no shared cache — acceptable at single-bundle/hundreds-of-nodes scale
(the same scale argument ADR 0004 makes for the flat vector store), revisit only
if okfctl ever serves multiple concurrent consumers at real scale.

## 2. API surface

Base path: everything lives under `/api/v1/...` (no path-shape churn later; a v2
mount point does not have to touch v1 routes). All responses are `application/json;
charset=utf-8` unless noted. All list endpoints return a stable, deterministic
order (same discipline as `graph export`/`search --json`: sorted, not map-order).

### 2.1 Corpus stats — `GET /api/v1/stats`

Replaces nothing (concepts.json/index.json today carry stats implicitly by
count); this is a first-class summary endpoint, cheap enough to poll for a
dashboard header widget.

```
$ curl -s http://127.0.0.1:8931/api/v1/stats | jq
```
```json
{
  "schema": 1,
  "bundle_root": "/Users/caseywest/src/knowledge-base/bundles/knowledge",
  "okf_version": "0.1",
  "node_count": 239,
  "edge_count": 512,
  "orphan_count": 3,
  "neighborhoods": [
    {"name": "casey", "count": 41},
    {"name": "content", "count": 12},
    {"name": "design", "count": 18},
    {"name": "domains", "count": 9},
    {"name": "infra", "count": 22},
    {"name": "integrations", "count": 14},
    {"name": "method", "count": 27},
    {"name": "research", "count": 31},
    {"name": "security", "count": 19},
    {"name": "wine", "count": 46}
  ],
  "types": [
    {"name": "Concept", "count": 231},
    {"name": "Playbook", "count": 8}
  ],
  "generated_at": "2026-08-02T18:41:12Z",
  "index_healthy": true

```
`okf_version` is read straight from the bundle's `.okf` sidecar
(`Bundle.OkfVersion`, already parsed by core) — not hardcoded, so a future v0.2
corpus reports itself correctly without a code change here. `index_healthy`
reflects whether `.okfctl/index.db` exists and its recorded model/dim are
loadable (surface for a dashboard health chip); it does not build the index on
the stats path.

### 2.2 List nodes (paginated, filterable) — `GET /api/v1/nodes`

Replaces `index.json`'s `concepts` array as a live, filterable, paginated
resource instead of one static blob.

Query params:

| Param | Meaning | Default |
|---|---|---|
| `type` | exact match on `type` (repeatable: `?type=Concept&type=Playbook` = OR) | none |
| `neighborhood` | exact match on first path segment | none |
| `tag` | node has this tag (repeatable, AND semantics — narrows) | none |
| `status` | `draft\|stable\|deprecated` (derived per §5.4 of the spec via `Node.Status()`) | none |
| `q` | lexical substring, delegates to `okf.Search` field `any` | none |
| `page` | 1-indexed page number | `1` |
| `per_page` | page size, capped at `200` | `50` |
| `sort` | `path` (default) \| `modified` \| `title` | `path` |

```
$ curl -s 'http://127.0.0.1:8931/api/v1/nodes?type=Playbook&per_page=2' | jq
```
```json
{
  "schema": 1,
  "page": 1,
  "per_page": 2,
  "total": 8,
  "total_pages": 4,
  "nodes": [
    {
      "path": "method/agentic-delivery-lifecycle.md",
      "title": "The Agentic Delivery Lifecycle (ADLC)",
      "type": "Playbook",
      "neighborhood": "method",
      "status": "stable",
      "modified": "2026-06-23T00:00:00Z",
      "tags": ["adlc", "governance", "autonomy"],
      "aliases": ["ADLC", "agentic delivery lifecycle"],
      "orphan": false
    },
    {
      "path": "method/economy-of-action.md",
      "title": "Economy of Action",
      "type": "Playbook",
      "neighborhood": "method",
      "status": "stable",
      "modified": "2026-06-20T00:00:00Z",
      "tags": ["efficiency"],
      "aliases": [],
      "orphan": false
    }
  ]
}
```
`status` here is `Node.Status()` from `internal/okf/provenance.go` (§5.4, defaults
`stable` when absent) — **not** the office's current `authority` field
(`VERIFIED`/`NUANCED`/...), which is a KB-house-convention frontmatter key with no
OKF spec meaning. See §2.9 on why that split matters and what the API does about
it.

### 2.3 Single node — `GET /api/v1/nodes/{path}`

`{path}` is URL-escaped, bundle-relative (e.g. `wine%2Ftannin.md`); accept both a
`.md`-suffixed and bare form and normalize server-side (a dashboard building links
from `graph.json`'s bare ids like `casey/agentic-manifesto` should not have to know
the parser's exact path convention). 404 with a JSON error body on unknown path —
never a bare empty body, so the dashboard can render a real "not found."

Query param `body=raw|rendered` (default `raw`): `raw` returns the Markdown
source as-is (parity with office's current `concepts.json` design choice — "the
body is the markdown source... rendering stays on the consumer side of the seam");
`rendered` returns server-rendered HTML via goldmark (already a dependency,
`goldmark-meta` is wired in core per the walking-skeleton plan) for a consumer that
doesn't want to ship a Markdown renderer. Both are on the same endpoint via a
query flag rather than two routes, since it's the same resource at two
representations.

```
$ curl -s 'http://127.0.0.1:8931/api/v1/nodes/casey%2Fagentic-manifesto.md' | jq
```
```json
{
  "schema": 1,
  "path": "casey/agentic-manifesto.md",
  "title": "The Agentic Manifesto",
  "type": "Concept",
  "neighborhood": "casey",
  "frontmatter": {
    "type": "Concept",
    "title": "The Agentic Manifesto",
    "tags": ["agentic", "manifesto"],
    "modified": "2026-06-21T00:00:00Z",
    "authority": "VERIFIED"
  },
  "body": "# The Agentic Manifesto\n\n...",
  "body_format": "raw",
  "out_links": ["casey/agentic-delivery-lifecycle.md", "casey/determinism-gap.md"],
  "backlinks": ["casey/agentic-delivery-lifecycle.md"],
  "orphan": false,
  "provenance": {
    "status": "stable",
    "trust_tier": "unverified",
    "stale": false,
    "generated": null,
    "verified": [],
    "sources": []
  },
  "etag": "\"6f2c9a1e...\""
}
```
`frontmatter` is the raw parsed map, unfiltered — this is the seam that lets a
KB-house-specific field like `authority` (used today by office's `graph.json` and
`index.json`) pass through **without the API inventing a schema for it**: the API
does not promote `authority` to a first-class field because it is not an OKF spec
concept (see §2.9); it is simply visible inside `frontmatter` like every other
key, spec-defined or not. `provenance` is the *only* place the API adds derived
fields, and every one of them is backed by an accessor already implemented in
`internal/okf/provenance.go` (§5 of the v0.2 spec, read with v0.1 fallback) —
nothing new is invented here, this endpoint just returns what
`Node.Status()/TrustTier()/IsStale()/Generated()/Verified()/Sources()` already
compute.

### 2.4 Graph — `GET /api/v1/graph`

Thin JSON wrapper over `okf.BuildGraph(b)` — the *exact* same serializer `graph
export --format json` and `serve`'s `/graph.json` already use, so the API's graph
view can never disagree with the CLI's. No new graph-building code.

```
$ curl -s http://127.0.0.1:8931/api/v1/graph | jq '.nodes[0], .edges[0]'
```
```json
{"path": "casey/agentic-delivery-lifecycle.md", "title": "...", "type": "Concept", "neighborhood": "casey", "orphan": false}
{"from": "casey/agentic-delivery-lifecycle.md", "to": "casey/agentic-manifesto.md"}
```
Optional `?type=` / `?neighborhood=` filters on **nodes only** (edges between two
filtered-out nodes are dropped, edges to a filtered-out node are kept with a
`"dangling": true` marker) — this lets office's canvas request "just the `wine`
neighborhood" without transferring the whole 239-node graph for a filtered view.

### 2.5 Backlinks — `GET /api/v1/nodes/{path}/backlinks`

A dedicated endpoint even though `GET /nodes/{path}` already inlines `backlinks`,
because a "what links here" widget is a common enough dashboard need to deserve
its own cheap, cacheable URL independent of fetching the whole node body:

```json
{"schema": 1, "path": "casey/agentic-manifesto.md",
 "backlinks": [{"path": "casey/agentic-delivery-lifecycle.md", "title": "The Agentic Delivery Lifecycle (ADLC)"}]}
```

### 2.6 Neighborhood traversal — `GET /api/v1/nodes/{path}/neighbors?depth=1`

Thin wrapper over `okf.Neighborhood` (already core, already undirected, already
depth-clamped):

```json
{"schema": 1, "path": "casey/agentic-manifesto.md", "depth": 1,
 "neighbors": [
   {"path": "casey/determinism-gap.md", "title": "Determinism Gap", "type": "Concept", "neighborhood": "casey", "depth": 1}
 ]}
```

### 2.7 Search — `GET /api/v1/search`

**One endpoint, two modes selected by params** (mirrors `okfctl search`'s own
lexical-vs-`--neighbors` split, and composes rather than reinvents):

- `?q=<term>&field=any|title|tag|type|body` — lexical, delegates to
  `okf.Search`.
- `?semantic=<term>&k=5` — semantic, delegates to `search.Query` against the
  bundle's `.okfctl/index.db` flat store (§4 explains how the index gets built and
  who owns rebuilding it).

Both share one response shape (`results`), tagged with `"mode"` so a client can
tell which ranking produced them without out-of-band knowledge:

```
$ curl -s 'http://127.0.0.1:8931/api/v1/search?semantic=natural%20wine%20tannin&k=3' | jq
```
```json
{
  "schema": 1,
  "mode": "semantic",
  "model": "model2vec-potion-base-8m",
  "query": "natural wine tannin",
  "results": [
    {"path": "wine/tannin.md", "title": "Tannin", "type": "Concept", "neighborhood": "wine", "score": 0.912},
    {"path": "wine/natural-wine.md", "title": "Natural Wine", "type": "Concept", "neighborhood": "wine", "score": 0.845},
    {"path": "wine/acidity.md", "title": "Acidity", "type": "Concept", "neighborhood": "wine", "score": 0.611}
  ]
}
```
```
$ curl -s 'http://127.0.0.1:8931/api/v1/search?q=tannin&field=body' | jq
```
```json
{
  "schema": 1,
  "mode": "lexical",
  "query": "tannin",
  "results": [
    {"path": "wine/tannin.md", "title": "Tannin", "type": "Concept", "neighborhood": "wine", "matched_on": ["body", "title"]}
  ]
}
```
Requesting `?semantic=` when no index exists returns **`503 Service Unavailable`**
with a body explaining how to build one (`okfctl-search index build`, or let
`okfctl-api` build it lazily — see §4), never a silent empty result set: an empty
`results: []` must always mean "the query matched nothing," never "the feature
isn't wired up." That distinction is the same discipline `okfctl-search`'s
model-mismatch guard already applies to its own callers (ADR 0004: "a query issued
against a mismatched-model index is rejected rather than silently wrong").

### 2.8 Freshness / provenance — `GET /api/v1/freshness`

The dashboard's "how stale is this dashboard, and how stale is the corpus"
question, in one endpoint, folding together three orthogonal signals the office
currently has none of a live view on:

```json
{
  "schema": 1,
  "bundle_loaded_at": "2026-08-02T18:30:00Z",
  "bundle_watch": {"mode": "fsnotify", "last_reload_at": "2026-08-02T18:41:00Z", "reload_count": 3},
  "okf_version": "0.1",
  "git": {
    "sha": "b54a456",
    "committed_at": "2026-08-02T14:12:09Z",
    "clean": true
  },
  "index": {
    "present": true,
    "model": "model2vec-potion-base-8m",
    "dim": 256,
    "entry_count": 239,
    "stale_entry_count": 0
  },
  "stale_nodes": 4
}
```
`stale_nodes` is the count of nodes where `Node.IsStale(time.Now())` is true
(§5.5 `stale_after`) — again, purely a read through the existing provenance
accessors, computed once per bundle (re)load and cached, not per-request.
`git.*` is best-effort: if the bundle root isn't inside a git work tree (or `git`
isn't on PATH), the whole `git` object is `null`, not an error — the same
degrade-outside-git posture `internal/okf/gitmeta.go` already establishes for the
validate-drift check.

**On OKF v0.2 provenance fields:** yes, expose them (`sources`, `generated`,
`verified`, `status`, `stale_after`, derived `trust_tier`) via the accessors in
§2.3/§2.8, but **only as already-implemented reads, never as new spec behavior.**
This is squarely inside the "known open gap, do not close it" boundary: the real
corpus is v0.1 and simply won't populate these fields today (`Generated()`/
`Verified()`/`Sources()` will mostly return zero values via the v0.1 fallbacks),
and that's fine — the API surfaces whatever `internal/okf/provenance.go` already
computes for whatever the bundle actually declares (`Bundle.OkfVersion`), and does
not attempt to backfill, migrate, or require v0.2 fields to be present. When the
tracked v0.1→v0.2 migration work lands (there's already a two-phase migrate path
per `d75e8d1`), this API surface picks up richer values automatically with **zero
API changes** — the schema already has the fields, they're just empty/default
today. That is the correct shape for "do not close the gap as a side effect."

### 2.9 A field that does *not* get promoted: `authority`

office's current `graph.json`/`index.json`/`concepts.json` all carry an
`authority` field (`VERIFIED`, `NUANCED`, `SPECULATIVE`, etc.) sourced from a
KB-house frontmatter convention, not the OKF spec. `okfctl` must not invent this
as a first-class concept — doing so would be exactly the over-conformance trap
AGENTS.md calls out ("puts anything beyond [the spec floor] behind an explicit
opt-in overlay that never leaks into the floor"). The API's answer: `authority`
stays reachable through the generic `frontmatter` map on `GET /nodes/{path}` and
is **not** added as a queryable/filterable first-class field on the collection
endpoints. If office wants to filter or sort by `authority` server-side later,
that's a `--templates`-style opt-in overlay this proposal deliberately leaves out
of v1, not a tacit house taxonomy baked into the wire schema.

## 3. Protocol, caching, watching

### 3.1 Protocol: plain REST + JSON — rejecting JSON:API, GraphQL, gRPC

- **JSON:API** — rejected. Its resource-object/relationships/included envelope
  buys standardized pagination/linking conventions this proposal already
  hand-rolls simply (offset pagination, inline nested fields), at the cost of a
  much heavier response shape for a single-consumer API with one client (the
  office dashboard) that isn't asking for it. Not worth the ceremony at this
  scale.
- **GraphQL** — rejected. It would be a genuinely good fit for "let the dashboard
  ask for exactly the fields/depth it wants" (nodes + backlinks + neighbors in one
  round trip), but it requires a schema layer, a resolver graph, and (in Go) a
  non-stdlib library (`gqlgen` or similar) — direct tension with `okfctl`'s
  stdlib-first, minimal-dependency posture (ADR 0001, PRD §5.1) for what would be
  the *first* non-stdlib HTTP dependency in the whole project. `serve` already
  proves plain `net/http` + `http.ServeMux` is sufficient for this project's
  ambitions; there's no evidence office's dashboard needs GraphQL's flexibility
  over a half-dozen REST endpoints.
- **gRPC** — rejected outright. Wrong shape for a browser-based dashboard talking
  over HTTP behind Caddy; would need a gRPC-Web shim for zero benefit. No case for
  it here.
- **Chosen: REST + JSON over stdlib `net/http`**, `http.ServeMux` route
  patterns (`GET /api/v1/nodes/{path...}` — Go 1.22+ mux patterns are already
  implicitly available since the walking-skeleton plan targets Go 1.26). Zero new
  non-stdlib HTTP dependencies. This exactly matches the `serve` command's
  existing architecture (ADR 0006's backend half) — same stack, no framework, one
  more mux.

### 3.2 Also emit a static snapshot for a static-first consumer

Ship a `GET /api/v1/snapshot` endpoint (and a CLI-invokable equivalent,
`okfctl-api snapshot --out data/`) that renders the *exact same JSON shapes* the
live endpoints serve, flattened to files on disk — deliberately shaped as a
**drop-in replacement for office's current `data/*.json`, byte-for-byte-comparable
in intent** (not identical field names, since the API's schema is the new
contract office adopts — see §6). This exists for one reason: office's own
deploy story explicitly values "self-contained static site, no build step on the
serving box" (`office_data/README.md`: "the tailnet server needs no build step").
A live API server is a new moving part; a snapshot mode means the migration (§6)
can ship the static-fallback path on day one, decoupled from "is the live server
up right now."

`snapshot` is not a new code path: it's the same handler functions called
in-process against `httptest.ResponseRecorder` (or a lighter direct-call
refactor: handlers taking `(bundle, store, query) -> (any, error)`, wrapped once
for HTTP and once for a `json.Marshal`-to-file loop) — one implementation, two
invocations, so the static snapshot can never drift from the live shape by
construction, which is the same "one producer, `--check` guards it" discipline
`generate_data.py` already uses.

### 3.3 Caching / ETag

- Every node/collection response carries a strong `ETag` derived from the
  bundle's per-node content hash (`internal/okf` already computes content hashes
  for `okfctl-search`'s freshness keying, ADR 0004 — reuse it, don't recompute a
  parallel hash). `GET /api/v1/nodes/{path}` honors `If-None-Match` → `304`.
- Collection endpoints (`/nodes`, `/graph`, `/stats`) carry a bundle-generation
  ETag (a hash of the whole loaded bundle's node-path→content-hash map,
  recomputed once per (re)load, not per request) — cheap to compute, correct
  precision: any single node changing invalidates every collection's ETag,
  which is the conservative-correct answer for a corpus this size.
- `Cache-Control: no-cache` on everything (matches office's own
  `office_server.py` posture: "let the proxy/browser cache briefly but always
  revalidate so a regenerate is picked up promptly") — the ETag does the real
  work; `no-cache` just forces revalidation rather than trusting a `max-age`.

### 3.4 Bundle-change watching: fsnotify — vendor risk, and the mitigation

The bundle is a git checkout that changes when `office/server/refresh.py`
fast-forwards `~/src/knowledge-base` (today) or, more likely under this proposal,
whenever the corpus's own git remote is pushed to and pulled. `okfctl-api` needs
to notice and reload without a process restart.

**Recommendation: `fsnotify` (`fsnotify/fsnotify`), watching the bundle root
recursively.** This is a real tension worth naming plainly: it is the project's
*first* non-stdlib runtime dependency anywhere in the codebase (core, plugins, and
`internal/*` are stdlib-only today per ADR 0001/0004/0005). Weighed against the
alternative:

- **Polling (stat-based, stdlib-only)** — walk the bundle every N seconds,
  compare mtimes/content hashes, reload on change. Zero new dependencies, trivial
  to reason about and test, and *good enough* at hundreds-of-nodes scale (a full
  walk + stat of ~250 files costs low-single-digit milliseconds). The
  cost is reload latency bounded by the poll interval (e.g., up to 5s staleness)
  rather than near-instant.
- **fsnotify** — near-instant reload, no polling cost between changes, but a new
  dependency, and cross-platform behavior (inotify/kqueue/ReadDirectoryChangesW)
  that has historically had rough edges around recursive-watch and editor-atomic-
  rename patterns (a `git checkout`/`git merge --ff-only` replaces many files via
  rename, which fsnotify handles but needs care in the watch-list rebuild logic).

**Decision: start with polling (stdlib-only), not fsnotify, in the walking
skeleton (§7 Increment 2), and treat fsnotify as an explicit, ADR-gated upgrade
if reload latency becomes a real complaint.** This keeps `okfctl-api`'s first
shippable slice honest to the project's zero-new-dependency posture (the same
discipline ADR 0004/0005 rejected `sqlite-vec`/Python for) and defers the one
genuinely justified new dependency in this whole plugin until there's a concrete
reason to pay for it. A 2–5 second polling interval is invisible to a human
looking at a dashboard that only changes when someone pushes a knowledge-base
commit — this is not a a high-frequency editing workflow. If a future increment
adopts fsnotify, it gets its own ADR (mirroring ADR 0004's own future-revisit
clause), not a silent addition here.

Reload semantics either way: on detected change, reload the bundle into a **new**
`*okf.Bundle` off to the side, swap an atomic pointer once loading succeeds (never
serve a half-loaded bundle, never block in-flight requests on a reload), and bump
the collection ETag generation. The semantic index (`.okfctl/index.db`) is
**not** rebuilt automatically on every bundle reload (embedding is comparatively
expensive even with the pure-Go embedder) — see §4 for the index-refresh story.

## 4. Semantic search server-side

Reuse, don't reimplement: `okfctl-api` links `internal/search` directly (the same
package `okfctl-search` uses) — `search.Load`, `search.Query`, `search.Related`,
and the `Embedder` interface with its `HashEmbedder`/Model2Vec implementations
(ADR 0005: pure-Go, no Python/ONNX/CGO). No new embedding code.

**Index lifecycle for a long-running server** (different from `okfctl-search`'s
one-shot CLI invocation):

1. **At startup**, `okfctl-api` attempts `search.Load(bundleDir/.okfctl/index.db)`.
   If present and its recorded `model`/`dim` match the configured embedder, it's
   held in memory for the process lifetime (or until reload, below). If absent,
   semantic search endpoints return `503` until an index is built (§2.7) — never
   silently falling back to lexical, which would surprise a caller who explicitly
   asked for `?semantic=`.
2. **On bundle reload** (§3.4), the API does **not** eagerly re-embed. It reloads
   the *graph/lexical* view immediately (cheap) but marks the semantic index
   `stale_entry_count > 0` (visible in `GET /api/v1/freshness`, §2.8) until
   something rebuilds it. Re-embedding on every git-driven bundle reload would
   make every corpus push pay embedding latency inline with a request — wrong
   trade for a background service.
3. **Rebuilding is an explicit, out-of-band action**, not a query-time side
   effect: `POST /api/v1/search/reindex` (admin-only in intent, but see §5 on why
   this API does not implement auth — network-boundary-gated instead) triggers
   `search.BuildIndex(bundle, embedder, prevStore)` in a background goroutine
   (content-hash-keyed, so only changed nodes re-embed — ADR 0004's whole
   freshness discipline, reused verbatim) and swaps the loaded store atomically
   on completion. A GET-only mode ships in the walking skeleton (§7 Increment 4);
   `reindex` is a fast-follow once the read surface is solid, and can equally be
   triggered by `office`'s own `refresh.py` hook calling `okfctl-search index
   build` directly on the bundle and `okfctl-api` picking the new `index.db` up
   on its next scheduled stat-poll of that file (same poll loop as §3.4,
   watching one more path) — meaning **`reindex` over HTTP is a convenience, not
   a requirement**, because the CLI plugin can always do this job standalone.
4. **Embedder choice**: default to `HashEmbedder` only in tests/fixtures; in any
   real deployment `okfctl-api` should be configured with the same `model2vec`
   embedder (via `--embedder model2vec --model-path <dir>`, identical flags to
   `okfctl-search`, same config-file fallback via `okfconfig`) so the index it
   serves is byte-model-compatible with whatever `okfctl-search index build`
   produced on disk — one store, one model, whichever tool touches it last wins,
   exactly as ADR 0004's mismatch-guard already enforces at the `Load()` layer.

This design deliberately does zero new embedding/vector-store engineering: the
entire section is "point an HTTP handler at library calls that already exist,"
which is the payoff of building this as a plugin that links `internal/search`
rather than a subprocess wrapper around `okfctl-search`.

## 5. Auth, CORS, bind address — defer to the network boundary

office's own deployment model (per `deploy/caddy/blog.caddy` and the office's
architecture) is: **every upstream binds loopback only; Caddy terminates TLS and
is the sole thing exposed on the tailnet; tailnet membership is the access
control.** `office_server.py`'s own `is_loopback()` guard makes this explicit —
"the loopback bind IS the security model."

`okfctl-api` inherits this posture exactly, and should **not** try to be smarter
than its consumer's existing security boundary:

- **Bind address default: `127.0.0.1:8931`** (loopback, matching `serve`'s own
  `--addr 127.0.0.1:8080` default and office's `office_server.py`'s
  `DEFAULT_HOST = "127.0.0.1"`). Refuse a non-loopback `--addr` the same way
  `office_server.py`'s `make_server()` refuses one — `is_loopback()`-style guard
  before `net.Listen`, not merely a doc comment. This is a cheap, load-bearing
  safety net: it means a misconfigured `--addr 0.0.0.0` can never accidentally
  expose the corpus, matching the exact failure mode office's own server code
  already guards against.
- **No authentication in v1, and no authorization model.** The plugin does not
  implement API keys, bearer tokens, mTLS, or a user/role system. This is a
  deliberate, explicit non-goal, not an oversight: the tailnet + loopback-bind +
  Caddy-fronts-it model is *already* the access control for every other office
  upstream, and duplicating it inside `okfctl-api` would be two access-control
  systems that can drift out of sync (the worse failure mode) for zero
  additional real-world protection, since anyone who can reach the loopback port
  directly has already crossed the boundary that matters. If a future consumer
  needs per-user auth, that belongs in Caddy (which already terminates TLS and
  could add `basicauth`/forward-auth) or in a reverse-proxy layer in front of
  `okfctl-api`, never inside the plugin.
- **CORS: no `Access-Control-Allow-Origin` header by default**, i.e. same-origin
  only. The dashboard is expected to be served *by* Caddy at the same
  `office.caseywest.com` origin (or reverse-proxied under a path Caddy owns) that
  fronts `okfctl-api`'s loopback port — the office's existing pattern for every
  other upstream (`header_up Host` rewriting to match the canonical Host the
  upstream expects, per `blog.caddy`'s documented discipline). If office's
  dashboard JS calls `okfctl-api` cross-origin (a different subdomain from the
  page that serves it), CORS becomes Caddy's problem to solve with an explicit
  `header Access-Control-Allow-Origin` directive scoped to the known dashboard
  origin — not something `okfctl-api` guesses at with a wildcard, which would be
  the wrong default for a plugin whose only stated consumer is a same-operator
  tailnet dashboard.
- **Rate limiting / abuse protection: none.** Same reasoning — a tailnet-only,
  loopback-bound, Caddy-fronted service has no anonymous-internet threat model to
  defend against; adding rate limiting here would be solving a problem this
  deployment doesn't have.

The one thing `okfctl-api` *should* do defensively, independent of network
posture: **treat the bundle as read-only.** Every endpoint in this proposal is a
GET (or the one background-trigger `POST /reindex`, which mutates only the
derived `.okfctl/index.db`, never bundle source files). No endpoint writes
frontmatter, moves nodes, or touches `index.md`/`log.md` — mutation stays exactly
where it is today, in `okfctl node`/`index`/`log` commands run by a human or CI,
not in a network-facing API. This mirrors office's own board-safety discipline
(`generate_lab.py`'s `open_board_readonly`, which opens SQLite `mode=ro` so a bug
literally cannot write) — the same "read-only by construction, not by promise"
posture, here enforced by simply never wiring a write path rather than needing a
driver-level guard (there's no natural analog to SQLite's `mode=ro` for a
Markdown tree, so "never implement the write handler" is the equivalent
discipline).

## 6. Migration story for `cwest/office`

### 6.1 What gets deleted

Once `okfctl-api` ships its walking skeleton (§7) plus the snapshot mode (§3.2):

- **`office_data/_vendor/okf/`** (the entire vendored `corpus.py`/`embed.py`/
  `__init__.py` + `.okf-source-sha` + its README) — deleted outright. This is the
  duplication named in the task: office no longer needs its own copy of bundle
  parsing or embedding logic once `okfctl-api` is the single source of both.
- **`office_data/okf_bundle.py`** — deleted; it was already a thin re-export shim
  pointing at `rooms/knowledge-graph/okf_bundle.py`'s parser, which itself becomes
  redundant (see below).
- **`office_data/embeddings.py`** — deleted; embedding now happens inside
  `okfctl-api`/`okfctl-search`, not office Python.
- **`office_data/generate_data.py`** — deleted. Its five producer functions
  (`build_graph`, `build_index`, `build_concepts`, `build_log`, `build_search`)
  are superseded one-for-one by `okfctl-api` endpoints (`/graph`, `/nodes`,
  `/nodes/{path}`, — `log.json`'s git-log parsing has **no okfctl equivalent and
  is explicitly out of scope for this plugin**; see §6.3 below — and `/search`).
- **`rooms/knowledge-graph/okf_bundle.py`** (the canonical parser office's shim
  pointed at) — this is the deeper duplication: it's a *second*, independently
  written Python OKF parser, predating even the vendored `okf` package. It should
  be deleted in the same migration pass once every producer that depended on it
  (the knowledge-graph room's own `generate.py`, if it calls the parser directly
  rather than reading `data/graph.json`) is re-pointed at the API or the
  snapshot's `graph.json`-equivalent. **This is a larger, separate audit** (the
  knowledge-graph room predates the `office_data` seam and may have its own
  direct bundle-reading code paths not visible from `office_data/` alone) — call
  it out as its own follow-up card, not silently bundled into this migration.
- **`office_data/_vendor/__init__.py`**, `.pytest_cache` litter, `__pycache__` —
  deleted with the vendor dir.

### 6.2 What survives, and what the new data seam becomes

- **`office_data/generate_lab.py`** (board/team/services/stream) is **unaffected**
  — it reads live local Casey-box sources (kanban SQLite, `SOUL.md` profiles,
  launchd, cron), has nothing to do with the OKF bundle, and is out of scope for
  this proposal entirely.
- **The seam itself moves from "generated files office commits" to "live HTTP
  calls office's server-side code makes."** Concretely: `office/server/
  office_server.py`'s `_serve_data()` handler, which today reads
  `data/<name>.json` straight off disk, gains a thin proxy mode: requests to
  `/data/graph.json`, `/data/index.json`, `/data/concepts.json`, `/data/
  search.json` are satisfied by calling `okfctl-api` (`GET /api/v1/graph`,
  `/api/v1/nodes`, `/api/v1/nodes/{path}` fan-out or a bulk variant, `/api/v1/
  search`) and reshaping the response into the existing wire format **the
  front-end JS already expects** — so the dashboard's existing JS needs zero
  changes in the first migration pass. This is the seam discipline
  `office_data/README.md` already states as policy ("producers write it; the
  front-end reads it; neither knows how the other is implemented") — only the
  producer moves from a Python script to a Go HTTP call.
  - A follow-on pass (separate card, after the proxy is proven stable) updates
    the front-end JS to call `okfctl-api`'s native shapes directly and drops the
    translation shim — no reason to do both migrations in one PR.
- **`server/refresh.py`** shrinks dramatically: it no longer needs to fast-forward
  the knowledge-base clone and run `generate_data.py` (that's now `okfctl-api`'s
  own bundle-watch loop, §3.4, running continuously rather than on a timer). It
  keeps its role for the **lab layer** (`generate_lab.py` — unrelated) and for
  the **derived room artifacts** (`knowledge-graph`/`index`/`log`/`search`
  `dist/index.html` builds) *if* those rooms stay as separately-built static
  bundles rather than becoming direct `okfctl-api` consumers — a decision left to
  the office migration card, not this proposal.

### 6.3 The one artifact `okfctl-api` does not replace: `log.json`

`build_log()` in `generate_data.py` parses `git log` of the **knowledge-base git
repo** (commit history, Conventional+emoji subject parsing, PR numbers) — this is
git-history information, not OKF-bundle information, and `okfctl` has no concept
of it (the closest analog, `internal/okf/gitmeta.go`, only reads a single file's
last-commit-date for drift detection, not a changelog). **Recommendation: `log.json`
stays a small, standalone Python (or a new tiny Go) generator office keeps**,
decoupled from the vendored-`okf`-deletion — it was never actually part of the
duplication problem (it never imported the vendored `okf` package), so folding it
into this migration would conflate two unrelated cleanups. Call this out
explicitly to the office migration card so nobody assumes `okfctl-api` should grow
a `/log` endpoint it has no natural authority over.

### 6.4 Static fallback if the API is down

Because `okfctl-api snapshot --out data/` (§3.2) produces the same shapes the live
endpoints serve, office's migration should **keep committing a snapshot** the same
way it commits `data/*.json` today, just produced by `okfctl-api snapshot` instead
of `generate_data.py`, on the same `refresh.py`-hook cadence. `office_server.py`'s
`_serve_data()` proxy (§6.2) then degrades gracefully: try the live
`okfctl-api` call first (with a short timeout, e.g. 500ms); on any error
(connection refused, timeout, non-2xx), **fall back to the committed
`data/<name>.json` snapshot file already on disk** — the exact same file-serving
code path `office_server.py` has today, unmodified, just demoted from "the only
path" to "the fallback path." This gives office a live API without a
single-point-of-failure regression: if `okfctl-api` crashes or the box reboots
before the launchd job restarts it, the dashboard serves yesterday's snapshot
instead of a 502, which is a strict improvement over today's all-static baseline
(never worse, sometimes fresher).

## 7. Incremental delivery plan

Following the shape of `docs/plans/2026-07-24-{plugin-dispatch,graph-serve,
okfctl-search}.md`: TDD, per-task RED→GREEN→REFACTOR, signed commits, one
whole-increment E2E review gating each PR, real-corpus verification against
`~/src/knowledge-base/bundles/knowledge` before merge. Sized S (half a day or
less) / M (up to ~2 days) in the style those plans already use implicitly.

### Increment 1 (S) — walking skeleton: `okfctl-api serve` + `/stats` + `/graph`
- New `cmd/okfctl-api/main.go`, separate static binary, cobra root `okfctl-api`
  with `serve [bundle-dir] --addr 127.0.0.1:8931` (loopback-refusing bind guard
  copied in spirit from `office_server.py`'s `is_loopback`/`make_server`).
- `internal/apiserver/handler.go`: `newAPIHandler(b *okf.Bundle) http.Handler`
  (same pattern as `cmd/serve.go`'s `newServeHandler`, testable via `httptest`
  without binding a port).
- Endpoints: `GET /api/v1/stats`, `GET /api/v1/graph` (delegates to
  `okf.BuildGraph`, reuses `graphJSON`-equivalent serializer).
- `plugin list`/dispatch pick it up for free (ADR 0002's mechanism, zero new
  dispatch code) — verify `okfctl api serve` dispatches to it.
- Real-corpus check: `curl /api/v1/stats` against `~/src/knowledge-base/bundles/
  knowledge` reports `node_count` matching `okf_analyze.py`'s existing count.
- **Gate:** `gofmt -l`, `go vet`, `go test ./... -race`, `CGO_ENABLED=0 go build`,
  `go mod tidy -diff` (zero new deps this increment).

### Increment 2 (M) — full node/collection surface + polling reload
- `GET /api/v1/nodes` (pagination, `type`/`neighborhood`/`tag`/`status`/`q`
  filters, `page`/`per_page`/`sort`).
- `GET /api/v1/nodes/{path}` (raw + rendered body via goldmark; `frontmatter`
  passthrough; `provenance` block via `internal/okf/provenance.go` accessors).
- `GET /api/v1/nodes/{path}/backlinks`, `GET /api/v1/nodes/{path}/neighbors`.
- Bundle-change **polling** watcher (stdlib-only stat loop, §3.4), atomic bundle
  swap, collection-level ETag bump on reload.
- ETag/If-None-Match plumbing for `/nodes/{path}` and collection endpoints,
  content-hash-derived (reuse the hash `internal/search`/`okfctl-search` already
  computes for freshness keying — do not add a second hash function).
- Real-corpus check: paginate through all `~/src/knowledge-base` nodes at
  `per_page=50`, confirm `total` matches `stats.node_count`; confirm a touched
  file's ETag changes after the poll interval elapses without a restart.
- **Gate:** same three-layer gate as Increment 1, plus a v0.2 fixture run for the
  `provenance` block (AGENTS.md's "any change touching frontmatter or provenance
  must run against a v0.2 fixture" — the real corpus alone won't exercise it).

### Increment 3 (S) — lexical + semantic search endpoint
- `GET /api/v1/search` (both modes), delegating to `okf.Search`/`okf.Neighborhood`
  for lexical and `search.Query`/`search.Load` for semantic.
- `--embedder`/`--model-path` flags mirroring `okfctl-search` exactly (same flag
  names, same `okfconfig` fallback) so operational muscle memory transfers.
- `503` behavior when no index is present; explicit error body naming the fix
  (`okfctl-search index build`).
- Real-corpus check: build a real index with `okfctl-search index build` against
  `~/src/knowledge-base/bundles/knowledge`, confirm `okfctl-api`'s `?semantic=`
  results match `okfctl-search --semantic`'s own CLI output for the same query
  and `k` (same store, same code path — this should be a byte-for-byte score
  match, which is the actual regression test that proves "compose, don't
  duplicate" held).
- **Gate:** same, plus confirm `internal/apiserver` imports `internal/search` but
  introduces no new third-party dependency.

### Increment 4 (S) — `/freshness`, background reindex, snapshot mode
- `GET /api/v1/freshness` (git metadata via `internal/okf/gitmeta.go` reuse,
  index staleness, `stale_nodes` count via `Node.IsStale`).
- `POST /api/v1/search/reindex` (background goroutine, atomic store swap).
- `okfctl-api snapshot --out <dir>` CLI subcommand + `GET /api/v1/snapshot`
  producing the same JSON via the same handler functions (§3.2's
  one-implementation-two-invocations discipline).
- Real-corpus check: run `snapshot`, diff its output's node/edge counts against
  the live `/api/v1/graph` response — must be identical (same loaded bundle).
- **Gate:** full suite; confirm `reindex` is idempotent (second call with no
  content changes re-embeds zero nodes, per the content-hash-skip discipline).

### Increment 5 (M, owned by the `office` repo, not `okfctl`) — office migration
- Point `office_server.py`'s `_serve_data()` at `okfctl-api` with a
  snapshot-file fallback (§6.4).
- Delete `office_data/_vendor/okf/`, `office_data/okf_bundle.py`,
  `office_data/embeddings.py`, `office_data/generate_data.py` and their tests.
- Swap `refresh.py`'s data-layer regenerate step for `okfctl-api snapshot`
  (keeping the lab-layer step, `generate_lab.py`, untouched).
- Leave `rooms/knowledge-graph/okf_bundle.py` and `log.json`'s generator as
  explicitly flagged follow-up items (§6.1, §6.3) — not silently rolled into
  this increment.
- **Gate (office repo's own):** office's existing `--check` drift tests retargeted
  or deleted as appropriate; office CI no longer needs `model2vec`/`pyyaml` as
  data-layer deps (that weight moves entirely into `okfctl-api`'s Go binary).

Each increment ships as its own PR through the existing `okfctl` review lane
(topic branch off `main`, whole-increment E2E review, real-corpus proof pinned in
the PR body per AGENTS.md's definition of done) — no increment depends on a later
one shipping first, so the office side can start on Increment 5 as soon as
Increment 1–4 land, or even partially (proxy `/graph` and `/stats` first, add
`/search` when Increment 3 lands).
