# okfctl-api — make the read-only HTTP API v0.2-aware

**Status:** Approved (design) · **Owner:** Casey West · **License:** Apache-2.0
**Source of truth:** OKF `SPEC.md` **v0.2** §5.2 (generated), §5.4 (status
lifecycle), §11 (Conformance / unknown keys), §13.1 (v0.1 fallbacks). Upstream:
GoogleCloudPlatform/knowledge-catalog `okf/SPEC.md`.
**Base:** `main` @ `dc5e901`  **Branch:** `wt/t_68dbaa52`

## Problem

`okfctl-api` still carries a v0.1 mental model. `internal/apiserver/handler.go`
counts only `n.Type` into a distribution; the top-level `generated_at` field is
the RESPONSE clock at request time, not any node's §5.2 `generated.at`. Nothing
in the API reads `status` or `epistemic`. It passes on a v0.2 corpus only because
§11 tolerates unknown keys — "passing is not understanding." PR #60 made
validate/lint/analyze v0.2-aware but did NOT touch the API plugin.

## Goal (READ-ONLY, spec floor)

Teach the API to SURFACE the v0.2 provenance/lifecycle signals the in-memory
model already reads (`Node.Status()`, `Node.Epistemic()`, `Node.Generated()`).
No new spec rules, no enum-gating of an unknown key, no writer. v0.1 behavior
stays correct via the §13.1 fallbacks (negative control).

## Design

All changes live in `internal/apiserver/handler.go` and its tests; the shared
`okf.BuildGraph`/`GraphNode` serializer (also used by `graph export` and
`serve`'s `/graph.json`) is NOT touched — the API enriches its OWN `/graph`
payload, so the CLI's graph view is unchanged.

### 1. `/stats` — status lifecycle distribution (§5.4)

Add a `status` field: a `[]nameCount` of the §5.4 lifecycle status across the
same concept-node set the `types` distribution uses. Absent `status` ⇒ `stable`
(via `Node.Status()`). Sorted by name ascending — the same deterministic
convention `types`/`neighborhoods` follow. §5.4 names a CLOSED set
(`draft|stable|deprecated`), but the API only OBSERVES and never gates: an
out-of-enum value is reported as-is, never rejected (§11).

### 2. `/stats` — epistemic value distribution (§11 unknown key, observational)

Add an `epistemic` field mirroring analyze's `EpistemicReport`:
`{distribution: [{value, count}], untagged: N}`, ordered count DESC then value
ASC — the exact treatment PR #60 landed in `analyzeEpistemic`. `epistemic` is a
§11 unknown key; it is surfaced OBSERVATIONALLY and never enum-gated. Untagged
counts nodes carrying no `epistemic` key.

### 3. `/graph` — per-node §5.2 `generated.at`

Each `/graph` node payload gains a `generated_at` field carrying the node's real
§5.2 `generated.at` via `Node.Generated()`, with the §13.1 legacy `timestamp`
fallback. When neither is present (`ok == false`) the field is the empty string.
This is DISTINCT from the stats top-level response-clock `generated_at`: the two
never share a JSON object (one is a `/stats` top-level field, the other a
`/graph` per-node field), so there is no key collision and no silent overload.
The API `/graph` node is an apiserver-local type that EMBEDS the shared
`okf.GraphNode` and adds `generated_at`; edges are unchanged.

## Controls (both, every time)

- **POSITIVE** — a v0.2 fixture surfaces real status/epistemic distributions and
  per-node `generated.at`.
- **NEGATIVE** — a v0.1 fixture still serves correctly: `status` defaults to
  stable, `generated.at` resolves via the §13.1 `timestamp` fallback (or is empty
  when absent), and an unknown `epistemic` value is REPORTED, never rejected.

## Definition of done

- Response-clock `generated_at` and per-node `generated.at` unambiguous in the
  JSON shape.
- Real-corpus run against `~/src/knowledge-base/bundles/knowledge` with counts
